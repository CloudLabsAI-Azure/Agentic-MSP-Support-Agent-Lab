# Build Notes

> **Delivery path: Phase 8 of 8, maintain the lab.** The open questions below are settled during Phase 5, the pilot run ([SUPPORT-GUIDE.md](SUPPORT-GUIDE.md#phase-5-run-the-pilot)). Start of the path: [README.md](README.md#delivery-path).

**Who:** the lab author, and anyone reviewing a change to the lab. **Time:** about 20 minutes to read before any change.

Why this lab is built the way it is, what was verified, and what still needs a live deployment to confirm. Read this before changing the lab. The history of earlier versions is in [CHANGELOG.md](CHANGELOG.md).

## Source of truth

- Every technical step, UI label, role, license, price, limit and latency comes from the notes in `research/`, which were researched from Microsoft Learn, the Azure Retail Prices API and official product pages on 2026-11-06. Each note lists its sources with IDs, ends with its screenshot sources and an open questions list, and flags labels that differ between pages.
- Every record number, name, count and expected result comes from the seed manifest (`fixtures/seed/manifest.json` in the MCP server repository, generated by `setup/assets/labfiles/seed/generate_seed.py`). `setup/DATA-SPEC.md` lists the volumes and the records each exercise depends on.
- Where official pages disagree, the guide follows the most specific page and adds a Note that tells the participant what to look for if the label differs. The disagreements that affect a step are listed under [Open questions to settle in the pilot](#open-questions-to-settle-in-the-pilot).

## Scenario and audience

- The lab was requested by a Microsoft partner for MSP service desk engineers, automation engineers and solution architects: 4 workshops of up to 25 participants each, level 300, self-paced in a 4-hour window with no scheduled breaks and no instructor, followed by 24 hours in which the requester's reviewers judge the submitted work. The requester is never named in the lab; the story uses the fictional managed service provider **Relecloud Managed Services** and Microsoft's sample company names for its customers.
- The table of contents (7 exercises, 27 tasks, 104 steps) is fixed scope. Each guide step opens with the TOC step's text, adapted only from "your team" to "you", and the per-task minutes add up to each exercise's agreed duration (35, 25, 35, 50, 30, 30 and 15 minutes).
- Each exercise opens with one stakeholder question from Relecloud (the service desk manager, the support lead, the platform engineering lead, the head of service delivery, the CISO, the data protection officer and the managing director) and ends with **Apply It in Production**, because the audience builds and runs such systems. Exercise 7 ends with a business case that points back to evidence recorded in **Lab notes.txt** in every exercise.
- The environment is safe by default from the first minute: participants extend and test controls that already work, and no exercise asks them to fix a security exposure.

## Environment design decisions

| Decision | Choice | Why |
|---|---|---|
| Tenant and subscription model | One dedicated Microsoft Entra tenant with one Azure subscription per participant (CloudLabs Dedicated Tenant lab) | The requirements isolate every participant, including Entra ID and Purview. A subscription trusts exactly one tenant, so each tenant needs its own subscription, and a reset creates a new tenant and subscription (research-foundry 4.2) |
| Region | Canada Central, fallback Canada East | East US 2 and Sweden Central no longer accept new Azure AI Search services; Canada Central offers gpt-5.1 Global Standard, AI Search Basic with semantic ranker, API Management Developer and Container Apps (research-search, research-foundry) |
| Models | `gpt-5.1` (2025-11-13) Global Standard at 100,000 TPM and `text-embedding-3-small` Global Standard at 150,000 TPM | Bound by the requirements. A Free Tier subscription has no gpt-5.1 quota; Tier 1 allows 250,000 TPM. gpt-5.1 reasoning effort defaults to none and does not accept temperature (research-foundry) |
| Identity flow | OAuth identity passthrough on two Foundry project connections, used from the Foundry portal agent playground | Generally available and works in the playground. The agent-on-behalf-of-user flow is preview and does not run in the playground, so the design records passthrough as the closest working equivalent under the platform-dependency clause; the gateway adds the agent's ID from configuration so every log still names the agent (research-foundry 8) |
| Read and write separation | Two MCP tools on the agent: `servicedesk-read` (read tools only, no approval) and `servicedesk-write` (write tools only, approval on every call); the MCP server serves `/read/mcp` and `/write/mcp`, behind the API Management MCP APIs `servicedesk-read` and `servicedesk-write` | The requirements publish read and write tools on separate MCP tool connections set to no approval and approval required. Disjoint tool lists and separate gateway paths keep a write tool from ever appearing on the read connection (research-foundry 5) |
| Participant roles | The Senior Technician (the lab user) is a Global Administrator only while provisioning runs and holds no Entra directory role when the lab starts; the Tier 1 Technician never holds one. Azure, Foundry, Search, Key Vault, Log Analytics, Purview and Dataverse roles are listed in [setup/README.md](setup/README.md) | The requirements forbid tenant administrator roles for participants. Key Vault Reader shows that the secret exists without its value |
| Tenant setup | A certificate-based setup app is bootstrapped once, then everything runs app-only; the setup app removes the lab user's Global Administrator role last and strips its own privileges | A Global Administrator cannot remove their own role (research-purview-identity). A CloudLabs per-tenant service principal is supported as the preferred bootstrap if CloudLabs provides one |
| Dataverse environment | A managed developer environment per tenant, with Power Apps Premium for both technicians | From 2026-11-15 unmanaged developer environments can no longer be created, and managed environments need a premium license for every user who opens an app (research-dataverse) |
| Permission model | The MCP server's managed identity is a Dataverse application user with **Service Desk Agent Read**, **Service Desk Agent Write** and **Delegate**; it acts on behalf of the signed-in technician, so both roles must allow a change | Least privilege with read and write separated; Dataverse, not the agent, makes every authorization decision (research-dataverse) |
| Data protection baseline | The column security profile **Contact Phone Protection** secures the contact phone columns from the start; the MCP application user is never a member, so the agent never receives a phone number. Exercise 6 Task 1 extends the profile to the email column | The requirements protect contact fields with column security from the start |
| Denied attempts | The MCP server writes an **Agent Action** row (`spk_agentaction`) for every write attempt, allowed or denied | Dataverse auditing records only successful changes, so a denial would otherwise leave no Dataverse record (research-dataverse) |
| Duplicate submission | A repeated identical write with the same correlation ID within 10 minutes returns the first result and changes nothing | The requirements (Exhibit C) |
| Search export | Provisioning exports 753 searchable documents to Blob storage, one JSON file per document, before it loads the two new incidents; participants build the index in Exercise 1 | The requirements bind the Blob export; the new incidents must stay unseen by the index so the agent first meets them through the tools |
| Lead time | Environments and spares are provisioned at least 24 hours before each workshop | Sensitivity labels take up to 24 hours, DLP policies about an hour, Purview activity 60 to 90 minutes (research-purview-identity) |
| Microsoft Purview pay-as-you-go | Enabled per tenant in the Purview portal by the supplier | Portal only, for a Global Administrator, preview, and completion takes hours (research-purview-identity) |
| Lab VM | Standard_D2s_v5 with a Premium SSD P10 OS disk; no `Microsoft.DevTestLab/schedules` resource | The requirements bind D2s_v5; CloudLabs manages uptime |
| Template source | Bicep in `setup/bicep/`, compiled to `setup/deploy-01.json` by `setup/bicep/Build-Template.ps1` with a pinned compiler | The requirements list Bicep templates as a deliverable; CloudLabs deploys ARM JSON |
| Golden Environment | Version **v1.0**: every environment comes from the same template, lab files and MCP server release, and the readiness check reports the version | The requirements (Exhibit B) |

## Validation

- 14 graded tasks: 1.2, 2.1, 3.2, 3.4, 4.1 to 4.5, 5.3, 5.4, 6.1, 6.2 and 7.1. The search step reads the index statistics and the indexer status; the redeploy step reads the Container App revisions and `/health`; every other step reads the MCP server's tool invocation log in Log Analytics, so no step needs Dataverse permissions. Each step runs as the CloudLabs service principal, read-only, tries three times 60 seconds apart, and ends with a helpful message. See [validation-scripts/README.md](validation-scripts/README.md).
- Every task also has an **Expected results** checklist drawn from the seed manifest, every task of five minutes or more has **Troubleshooting**, and every exercise has **Success Criteria** with at least one negative check.
- `tests/acceptance/` proves the acceptance criteria that can be scripted (isolation, consistency, seeded data, grounded retrieval, read and write flow, redeploy and rollback, user authorization, secret handling, data protection, correlated audit) and gives timed checklists for the rest.

## Diagrams

- 9 animated diagrams: `session-journey` (README and agenda), `architecture` (getting started and README), and one per exercise: `exercise-1-grounding`, `exercise-2-ticket-intelligence`, `exercise-3-mcp-read-path`, `exercise-4-approval-flow`, `exercise-5-identity-token-flow`, `exercise-6-protection-and-trail` and `exercise-7-end-to-end`. They are authored as code in `tools/diagrams/build_diagrams.py` with the toolkit `tools/diagrams/svgkit.py`, which writes the SVG sources to `Instructions/media/`. `tools/diagrams/Render-Diagrams.ps1` renders each SVG to an animated PNG beside it, because not every guide renderer animates SVG; GitHub animates the SVGs in the README.
- Regenerate after editing a diagram: `python tools/diagrams/build_diagrams.py`, then `pwsh -File tools/diagrams/Render-Diagrams.ps1 -Name <name>`. The official icon packs are downloaded by `tools/diagrams/Get-ProductIcons.ps1` and are never committed; every diagram embeds the icons it uses.
- Every record number and name in a diagram comes from the seed manifest, and every "How to read this diagram" paragraph in the guide matches the diagram's text. Change both together.
- Correlation IDs and terminal output in the diagrams are illustrative and labeled as such.

## Known lint findings that are expected

- **ScreenshotPending:** every screenshot is a pending marker until the pilot capture pass; [SCREENSHOT-TODO.md](SCREENSHOT-TODO.md) lists them.
- **ValidationPlaceholder:** `REPLACE-WITH-VALIDATION-GUID` stays in the 14 graded tasks until the steps are registered in Phase 4.
- **Placeholder in the search definitions:** `setup/assets/labfiles/search/*.json` hold `{{EmbeddingResourceUri}}`, `{{SubscriptionId}}`, `{{ExportContainer}}`, `{{SearchIndex}}` and similar fields on purpose: `New-KnowledgeIndex.ps1` fills them from `C:\LabFiles\lab-settings.json` when it creates the objects.
- **Placeholder in `setup/deploy-01.json`:** the doubled braces in the role-assignment conditions of the custom RBAC role are ARM's escape for a literal brace inside `format()`, not placeholders.
- **UserCreationJson:** `setup/scripts/user-creation.json` keeps `REPLACE-WITH-CSP-OFFER-ID-...` until CloudLabs gives the Microsoft 365 E5 and Power Apps Premium offer IDs ([setup/README.md](setup/README.md#questions-for-cloudlabs), question 4). Replace them before the first deployment.
- **qa-scan marker warnings on two-shot steps:** steps with two screenshots use IDs such as `E6T1S1-1` and `E6T1S1-2`, which `references/screenshots.md` and the lint accept, while the ID pattern in `tools/qa/qa-scan.py` doesn't yet. They disappear when the pilot replaces the markers with images.

## Open questions to settle in the pilot

Each item names the step it affects and the fallback the build already has. Replace the question with the answer and its date, update the guide where the answer changes a step, and record it in the [pilot log](#pilot-log).

1. **Lab user credential.** Is `AzureAdUserPassword` a password or a Temporary Access Pass? The one-time setup app bootstrap signs in with it (setup; fallback: a CloudLabs per-tenant service principal through the template's bootstrap parameters, the preferred option).
1. **License offer IDs.** No verified CSP offer ID exists yet for Microsoft 365 E5 or Power Apps Premium in the user-creation JSON (setup; fallback: CloudLabs confirms the IDs before the pilot; never copy an unconfirmed ID).
1. **Security defaults and Conditional Access** in new CloudLabs tenants must not block the bootstrap sign-in or the participants' Temporary Access Pass (setup and getting started).
1. **Purview pay-as-you-go timing.** How long the per-tenant enablement takes, and whether `processContent` already blocks before it completes (Exercise 6 Task 2; fallback: enable it the day before with the environments).
1. **Where the DLP event lands and when.** DLP Activity explorer, the DSPM AI activities view, or both, and the real delay for an Entra-registered app (Exercise 6 Task 2 step 5; fallback: the MCP log entry, which is immediate, and a second look after Exercise 7).
1. **Viewer access to the DLP policy.** Whether a PowerShell-created application DLP policy is visible to **Information Protection Analysts** (Exercise 6 Task 2 step 1; fallback: the policy and rule printed in the provisioning log).
1. **Column security under impersonation.** Whether Dataverse evaluates field security for both the MCP application user and the impersonated technician (Exercise 6 Task 1 and the phone baseline; fallback: the MCP server's own filter on secured columns).
1. **Depth under impersonation.** Whether narrowing **Service Desk Agent Write** to Business Unit depth blocks the Senior Technician's change on a Relecloud Regulated Accounts record, and the exact error code and message (Exercise 5 Task 3; capture the real string for the expected result).
1. **Security Steward rights.** Whether the custom **Service Desk Security Steward** role can open the environment in the Power Platform admin center and its solution in Power Apps, edit a role's depth, secure a column, publish customizations and edit a column security profile (Exercise 5 Tasks 1 and 3, Exercise 6 Task 1; fallback: the template parameter `seniorDataverseSystemAdministrator`, which gives System Administrator in that Dataverse environment only and then bypasses column security for that user in the app).
1. **Exercise timing.** Exercise 5 Task 1 and Exercise 6 Task 3 carry a lot of portal navigation for their minutes; time them in the pilot walkthrough and move detail into Notes if they run long.
1. **Tier 1 in the playground.** Whether **Foundry Agent Consumer** is enough for the Tier 1 Technician to use the portal playground (Exercise 5 Task 4; fallback: the template parameter `tier1FoundryRole` set to **Foundry User**).
1. **The approval prompt.** What the playground shows for a write (server, tool, full arguments) and the name of the decline control (Exercise 4 Task 1; capture it for the guide and the screenshots).
1. **Approval expiry.** How long an unanswered approval stays open, and what happens to a new message while one is pending (Exercise 4; the requirements need the expiry confirmed in the design pack).
1. **Duplicate key.** Whether Agent Service retries a tool call or passes a stable call ID, given that the gateway issues a new correlation ID per request (Exercise 4; acceptance criterion 6).
1. **Knowledge in the portal.** The Foundry portal path for adding Azure AI Search to a text prompt agent (Exercise 1 Task 2; the guide uses `Update-AgentDefinition.ps1` and shows the portal result).
1. **Keyless search roles.** Whether the agent's search connection needs the role on the Foundry account identity, the project identity, or both (Exercise 1 Task 2; provisioning assigns both).
1. **Embedding output path.** `/document/contentVector` in the skillset (Exercise 1 Task 2; `New-KnowledgeIndex.ps1` fails loudly if no vectors land).
1. **Indexer duration** for 753 documents when 25 or more search services index at the same time in one region (Exercise 1 Task 2; the script waits and can be rerun safely).
1. **Gateway logs.** Whether the Developer tier writes `ApiManagementGatewayMCPLog` rows, and whether `CorrelationId` equals the `x-correlation-id` the policy sets (Exercise 3 Task 2, Exercise 6 Task 3; the queries match both).
1. **Key Vault audit table.** `AZKVAuditLogs` or `AzureDiagnostics` (Exercise 5 Task 2; the query unions both).
1. **Rollback in single revision mode.** Whether `az containerapp revision copy` from a deprovisioned revision works (Exercise 3 Task 4; fallback: redeploy the previous image tag).
1. **Build and revision timings.** `az acr build` plus revision readiness against the 15-minute redeploy task and the Exercise 4 redeploys.
1. **Token use.** gpt-5.1 reasoning effort, playground evaluators, and the real tokens per participant against the allowance of 4 million input and 0.4 million output tokens. The estimate assumes about 2 million input tokens per participant ([estimates/ESTIMATE-NOTES.md](estimates/ESTIMATE-NOTES.md)). Check in one trace whether Foundry sends the MCP tools' output schemas to the model with every call: if it does, they add about 31,700 tokens per call and push a participant past the allowance, and the schemas must be trimmed.
1. **Provisioning time** per environment against the 60-minute reset and the 15-minute spare replacement (acceptance criteria 12 and 14).
1. **Managed developer environment creation** through the Power Platform API in a brand-new tenant after 2026-11-15, including the admin role cache (setup).
1. **Data processing location.** Global Standard may process prompts in any region, and Data Zone is not offered in Canada; confirm with the requester that this is acceptable (design).

## How to change the lab

| Change | Where | Then |
|---|---|---|
| A step, label or screenshot in the guide | `Instructions/*.md`, `Instructions/media/` | Run the CloudLabs lint (`lint-lab.ps1 -Path .`), `python tools/qa/qa-scan.py .` and `python tools/qa/check_links.py .`, then regenerate the screenshot inventory: `python tools/qa/make_screenshot_todo.py .` |
| A diagram | `tools/diagrams/build_diagrams.py` | `python tools/diagrams/build_diagrams.py`, then `pwsh -File tools/diagrams/Render-Diagrams.ps1 -Name <name>`, and update the "How to read this diagram" paragraph |
| Seed data | `setup/assets/labfiles/seed/` | Regenerate, run `setup/tests/test_seed_determinism.py`, copy the fixtures to the MCP server repository, update `setup/DATA-SPEC.md`, and check every expected result that quotes the changed records |
| The MCP server | The `agentic-msp-mcp-server` repository | Run its tests, tag a new release, rebuild the lab files zip with `setup/Build-LabFilesZip.ps1 -McpRelease <tag>`, check it with `python tools/qa/check-labfiles-zip.py . setup/assets/msp-labfiles.zip --allow-file tools/qa/labfiles-allow.txt`, and update the release tag the template, the readiness check and the validation steps expect |
| Azure resources or template outputs | `setup/bicep/` | `pwsh -File setup/bicep/Build-Template.ps1` to compile `setup/deploy-01.json`, upload it, and deploy one lab; outputs are the Environment tab fields the guide names |
| Tenant configuration (roles, Purview, Dataverse, agent, connections) | `setup/assets/labfiles/provision/` and `setup/tenant/` | Change the guide, the provisioning scripts, the readiness check, the runbooks and the validation steps together: they look for the same names |
| A graded task | `validation-scripts/*.ps1` | Paste the script into the CloudLabs step again, **DEPLOY ALL STEPS**, and test it negative then positive ([validation-scripts/README.md](validation-scripts/README.md)) |
| The Golden Environment version | Template output **Golden Environment Version**, `lab-settings.json`, the readiness check | Bump the version whenever the template, lab files or MCP release change, and record it in [CHANGELOG.md](CHANGELOG.md) |
| Prices or licenses | `research/`, `estimates/*.json` | Regenerate the estimate workbooks with the Lab Builder generators |
